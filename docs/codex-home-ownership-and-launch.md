# Codex Home 所有权与启动流程

## 状态

- 设计状态：已确认
- 实现状态：1.2.63 实现默认 `.codex` 单工作区绑定、既有目录保护、隔离档案、安全迁移，以及安装完成后的桌面自动打开与可见窗口校验
- 适用组件：`baijimu-connector-codex`、Bridge Agent 本地应用启动与升级流程

本文定义 Codex 状态目录的所有权、首次初始化、百积木内启动、外部 Codex 行为以及显式切换规则。实现不得仅依据目录是否存在做覆盖决定，也不得把 Windows 用户环境广播放入 Connector 启动或健康检查路径。

## 目标

1. 首次使用 Codex 的用户无需理解 `CODEX_HOME`，从百积木启动即可使用。
2. 全新用户的首个百积木工作区直接绑定默认 `.codex`；该目录只允许绑定一个工作区，其他工作区使用短且隔离的私有路径。
3. 已有 Codex 用户的登录、配置、会话、MCP 和自定义目录不被覆盖。
4. 百积木启动的 Codex 始终使用明确选定的状态目录，不依赖 Explorer、终端或全局环境刷新。
5. Connector 必须在独占回环监听端口后同步创建并回读管理令牌，才能报告启动成功并开始提供 `/healthz`；后续初始化、`/readyz` 不依赖桌面应用、用户环境广播或其他 GUI 进程响应。

## 基本事实

- 未设置 `CODEX_HOME` 时，Codex 使用用户默认目录：
  - Windows：`%USERPROFILE%\.codex`
  - macOS/Linux：`$HOME/.codex`
- 进程环境属于进程自身。Connector 可以在启动 `codex app-server` 时显式传入 `CODEX_HOME`，该值会立即对其子进程生效。
- 写入 Windows `HKCU\Environment` 只是在注册表中持久化用户环境，不会修改已运行进程的环境块。
- `WM_SETTINGCHANGE` 只是通知 Explorer 等程序重新读取用户环境；它不能可靠地更新已经运行的 Codex 或终端。
- 因此，用户环境写入和广播都不是 Connector 可用性的前置条件。

## 权威状态与所有权

Connector 必须分别管理以下三类状态，不得相互推断：

1. 用户显式配置的 `CODEX_HOME`
   - 属于用户。
   - Connector 不得在后台覆盖、删除或改写。
2. 用户默认的 `.codex`
   - 可能不存在、为空、由百积木初始化，或者已经包含用户自己的 Codex 状态。
   - 目录存在本身不能代表已经完成初始化，也不能代表允许覆盖。
   - 仅当目录原本不存在，或有效所有权/预留标记能够证明属于同一档案时，Connector 才能绑定。
   - 一旦绑定，该工作区永久记录默认路径；切离后再切回仍使用默认 `.codex`。
3. Connector 私有状态目录
   - Connector 元数据和管理令牌位于 `BAIJIMU_CONNECTOR_DATA_DIR` 下。
   - 隔离的百积木工作区 Codex Home 位于用户目录下的 `.baijimu/codex/p/<短档案键>`。
   - 短档案键由权威 `profileId` 的 SHA-256 摘要确定性生成，不把环境、用户、客户端或工作区标识逐层拼入物理路径。
   - Windows 对应路径为 `%USERPROFILE%\.baijimu\codex\p\<短档案键>`。

默认 `.codex` 的所有权标记必须有效且不含秘密。标记至少包含：

- 固定的 schema 版本；
- 所有者标识 `baijimu-connector-codex`；
- 初始化时间；
- Connector 管理的文件清单；
- 由权威 `profileId` 计算的不可逆短档案键，用于校验唯一绑定；
- 不包含用户 ID、工作区 ID、凭证或环境地址原文。

在 `auth.json`、`config.toml` 和元数据提交完成前，Connector 使用独立的 pending 预留标记锁定同一短档案键。pending 标记不是完成所有权标记，初始化中断后只能由同一档案恢复，其他工作区不得接管。

工作区、用户、环境等可变业务数据必须来自 Connector 凭证元数据和平台授权结果，不得写成运行时分支或固定名单。

## 启动前状态判定

按以下顺序判定，不得只执行 `Test-Path ~/.codex`：

### 1. 用户已经显式设置 `CODEX_HOME`

- 将该路径视为用户所有。
- 不写入、不切换、不广播。
- 百积木使用 Connector 私有的工作区配置档案。
- 从百积木启动 `codex app-server` 时显式传入私有档案路径。

### 2. 新建百积木工作区档案

- 用户未显式设置 `CODEX_HOME` 且默认 `.codex` 不存在时，首个工作区预留并绑定默认 `.codex`。
- 默认 `.codex` 已存在但没有同一档案的有效所有权或预留标记时，视为用户所有，新工作区创建在 `.baijimu/codex/p/<短档案键>`。
- 默认 `.codex` 已由另一个百积木档案绑定时，新工作区同样使用隔离短路径，不能覆盖或复用默认目录。
- Connector 不在路径中暴露或重复环境、用户、客户端和工作区标识，也不设置或广播用户级 `CODEX_HOME`。
- 从百积木启动 `codex app-server` 或桌面 Codex 时，按单次进程显式传入该工作区已经登记的路径。

### 3. 迁移旧版 Connector 私有档案

- 仅迁移位于旧版 `BAIJIMU_CONNECTOR_DATA_DIR/codex-profiles` 根目录下、能够由 Connector 元数据证明归属的档案。
- 旧目录和新目录在同一文件系统时，通过目录整体重命名迁移，SQLite、会话、技能和其他状态不做逐文件重写。
- 升级自“所有工作区一律隔离”的版本时，如果默认 `.codex` 不存在、没有显式用户 Home、没有其他默认绑定，则把当前活动工作区整体迁移并绑定到默认 `.codex`。
- 先完成目录重命名，再原子写入元数据；若两步之间中断，下次启动依据“旧目录不存在、新目录存在”完成恢复。
- 如果当前活动档案仍位于旧目录，Connector 必须在启动就绪前先停止占用该目录的 Codex 桌面及其子进程，完成全部档案迁移和元数据提交后，再以迁移后的短路径恢复此前正在运行的桌面应用。
- 如果旧目录和新目录同时存在，停止迁移并保留两者，不覆盖、不合并、不删除。
- 已存在但无法证明百积木所有权的默认 `.codex`、显式自定义 `CODEX_HOME` 和其他外部目录不自动迁移。

### 4. 已绑定默认 `.codex` 的档案

- 元数据中的默认路径与带短档案键的所有权标记共同证明绑定，旧 schema 标记在已登记档案完成回查后升级。
- 切换到其他工作区不会改变绑定；切回时必须恢复默认 `.codex`。
- 用户从系统桌面或开始菜单直接启动 Codex 时，自然读取默认 `.codex`，因此进入该绑定工作区。

## 从百积木启动

用户点击 Bridge Agent 中的“启动应用”后：

1. Bridge Agent 启动并托管 Connector 进程。
2. Connector 独占绑定回环地址，但尚不接收 HTTP 请求。
3. Connector 在私有数据目录中加载或原子创建管理令牌，并回读确认文件内容与进程内值一致；失败时直接退出，不得报告启动成功。
4. Connector 进入初始化状态；`/healthz` 在初始化完成前不得报告就绪，此时 Bridge Agent 必须已经能够读取管理令牌。
5. Connector 只读检测旧档案迁移计划；若活动旧档案被桌面占用，先停止官方 Codex 桌面及其子进程。
6. Connector 加载所有权元数据，完成旧路径压缩迁移及符合条件的默认目录绑定迁移，并原子提交元数据；若此前桌面正在运行，以迁移后的最终路径恢复桌面。
7. Connector 根据上述状态判定选择本次使用的 Codex Home；初始化成功后 `/healthz` 和 `/readyz` 才返回成功。
8. 当会话能力需要 `codex app-server` 时，Connector 以子进程环境显式传入选定的 `CODEX_HOME`。
9. 子进程退出或工作区切换时，由 Connector 回收并按新档案重新启动。
10. 普通初始化完成 CLI、凭证、状态目录和能力验证后，如果目标工作区档案被正式激活，由 Connector 使用其已登记 `CODEX_HOME` 自动打开桌面应用。该动作发生在安装成功条件已经满足之后：系统应用激活失败不得把已完成的安装配置回退为初始化失败，Connector 必须保持 `succeeded`，记录安装器 warning，并提醒用户从系统应用列表手动打开 ChatGPT（部分版本名称为 Codex）。检测到既有个人配置而未激活工作区时，不打断已有桌面会话。安装脚本不拥有桌面进程启动权。升级迁移只恢复交接前已经运行的桌面实例，后续档案切换仍来自管理页的用户明确操作。

启动流程禁止：

- 持久写入用户级 `CODEX_HOME`；
- 在初始化、健康检查或非桌面激活流程中广播 `WM_SETTINGCHANGE`；
- 等待 Explorer、Codex Desktop、终端或其他 GUI 进程；
- 为了通过健康检查而隐藏凭证、目录或子进程启动错误。

## 切换规则

### 显式启动桌面 Codex

用户在工作区管理页选择个人 Codex 或百积木工作区时，Connector 可以重启官方桌面应用，使新进程读取所选状态目录。该操作必须：

1. macOS 使用系统应用启动入口；Windows 从已安装 Appx 清单读取其声明的全信任可执行入口。两者都不传入文件、目录或项目参数。
2. Windows 校验应用包来源、最低系统版本和 AppX 激活返回值；macOS 校验应用包与系统兼容性。系统激活请求被接受即返回，不同步等待进程或窗口就绪。
3. 将所选启动环境仅注入本次桌面启动；macOS 通过系统应用启动参数传递，Windows 在 AppX 激活前暂存并临时写入所需的用户环境值、广播环境变更，激活请求返回后逐项恢复原值并再次广播。任何原值、值类型或“原先不存在”的状态都必须精确恢复，不得留下持久环境变更。
4. 不把进程或窗口就绪作为同步成功条件，不把窗口置前或当前前台状态作为成功条件，也不创建 `~/Documents/Codex/default` 或任何其他合成项目来制造可见窗口。
5. 启动前移除继承的 `BAIJIMU_*`、`CODEX_CONNECTOR_*` 和父进程既有 `CODEX_HOME`，再只写入本次选择的 `CODEX_HOME`。正常桌面启动不得向进程注入用户级 CLI 授权文件或工作区环境，也不得修改授权文件或目录的 ACL。唯一例外是从 `1.3.16` 升级时执行一次精确撤销：读取当时被修改的 `sharedAuthPath`，只移除 Codex 沙箱主体的显式读取 ACL，记录完成后永久停止访问该路径。
6. 管理页显式切换时，启动命令失败必须使操作失败；这与安装收尾自动打开失败仍保持安装成功是两个不同契约。
7. 百积木工作区首次受管启动前，Connector 只把 `composer-permission-mode-visibility` 中的 `full-access` 设为可见，不修改 `permission-selection-by-host-id:*`，因此不会把 Ask for approval 自动切换为 Full access。兼容旧版布尔值和新版对象状态；Codex 引导尚未完成时保持迁移待处理，引导完成后再记录一次性迁移版本，后续尊重用户主动修改。

### 百积木内部切换工作区

- 更新 Connector 自己的活动档案元数据。
- 停止 Connector 托管的 `codex app-server`。
- 使用新档案路径显式设置子进程 `CODEX_HOME` 并重新启动。
- 不修改用户级环境，不广播，不影响外部 Codex。

### 外部 Codex 默认状态

产品不写用户级 `CODEX_HOME`。系统直接启动的 Codex 始终按自身规则读取默认目录：默认目录已绑定时进入对应百积木工作区；当前在 Connector 中选择隔离工作区时，系统另行启动的 Codex 仍读取默认绑定，不会跟随内部选择。

唯一允许的写入是旧版本迁移中的显式恢复：管理页确认当前值确实指向 Connector 私有档案后，按已保存的原始状态恢复“未设置”或原自定义路径，回读验证并记录完成时间；Windows 随后做一次有总时限的环境通知，并提示用户重启已打开的外部 Codex 和终端。该恢复不能被启动、健康检查或自动初始化隐式触发。

## 文件写入与安全约束

- 凭证必须通过私有临时文件或内存传递，日志、所有权标记和错误信息不得包含密钥。
- `auth.json`、`config.toml` 和所有权标记必须采用同目录临时文件加原子替换。
- Windows 应限制文件 ACL；Unix 应使用仅当前用户可读写的权限。
- 初始化任何一步失败时，不得留下看似完整的所有权标记。
- 只有全部必需文件写入并回读成功后，才能提交所有权标记。
- 已有用户文件不能用默认值整体覆盖；需要修改时必须按已声明的文件和字段所有权合并。

## 健康检查契约

- `/healthz`：进程已存活、管理令牌已落盘且能响应 HTTP，不依赖工作区凭证初始化或桌面状态。
- `/readyz`：Connector 的管理令牌、元数据和核心请求处理已经可用。
- 首次凭证安装、官方 Codex 安装和桌面启动属于可观察的 setup 状态，不得成为 Connector 进程存活的前置条件。
- Windows 环境广播不属于 health 或 readiness。
- Bridge Agent 应记录每次启动尝试、就绪失败正文和进程回收原因，界面必须能够查看完整错误。

## 初始化状态与恢复契约

- 每次初始化必须记录独立 `attemptId`、Connector 版本、开始/结束时间、稳定错误码和是否可重试；这些字段描述一次真实执行，不能由进程重启伪造。
- Connector 启动时不得无条件重写未变化的 `failed` 或 `succeeded` 状态，也不得因此刷新历史尝试的文件时间。
- 上次状态为 `running` 但执行进程已经消失时，必须迁移为 `interrupted`，保留历史错误仅供诊断，并由幂等 readiness 流程自动重新执行一次；同一恢复链再次中断后必须停止自动执行并等待用户重试，不得把中断冒充成当前安装失败或形成重启循环。
- 失败记录来自旧 Connector 版本时，必须迁移为 `needs_retry`，清除当前错误展示并重新验证；旧安装步骤不得作为新版本当前执行进度展示。
- 当前 Connector 版本产生的真实 `failed` 状态不得在每次启动时自动循环重装；界面必须提供显式修复动作。
- 初始化、状态加载和 Codex 启动等可恢复错误必须提供与原操作一致的重试动作。未授权工作区、缺少主体信息等前置条件错误只允许重新检查，不得触发安装。

## 旧版本迁移

旧版本可能已经把用户级 `CODEX_HOME` 指向 Connector 私有工作区目录。升级实现必须：

1. 读取现有凭证元数据中保存的原始环境状态。
2. 只有能证明当前值由 Connector 设置时，才允许执行恢复。
3. 不在后台启动或健康检查中静默修改用户环境。
4. 将恢复作为一次明确、可审计的迁移操作，并在完成后提示重启外部 Codex/终端。
5. 无法证明所有权时保持现状并提示用户处理，不得猜测或删除。

## 验收矩阵

至少覆盖以下自动化测试和 Windows 真机验证：

| 场景 | 默认 `.codex` | 用户级 `CODEX_HOME` | 百积木使用目录 | 外部 Codex | 广播 |
| --- | --- | --- | --- | --- | --- |
| 全新用户 | 不存在 | 未设置 | 默认 `.codex`，绑定首个工作区 | 使用同一绑定工作区 | 无 |
| 空目录但无标记 | 空 | 未设置 | `.baijimu/codex/p/<短档案键>` | 保持空目录 | 无 |
| 已绑定默认目录 | 有匹配档案键的有效所有权标记 | 未设置 | 已登记的默认 `.codex` | 使用同一绑定工作区 | 无 |
| 已有 Codex 用户 | 有用户状态、无标记 | 未设置 | `.baijimu/codex/p/<短档案键>` | 保持原状态 | 无 |
| 用户自定义 Home | 任意 | 已设置 | `.baijimu/codex/p/<短档案键>` | 保持用户自定义状态 | 无 |
| 第二个百积木工作区 | 已绑定首个工作区 | 未设置 | `.baijimu/codex/p/<短档案键>` | 仍使用首个绑定工作区 | 无 |
| 切回默认绑定工作区 | 已绑定 | 未设置 | 默认 `.codex` | 使用同一绑定工作区 | 无 |
| 旧版活动隔离档案迁移 | 不存在且无冲突 | 未设置 | 原子移动到默认 `.codex` 并绑定 | 使用同一绑定工作区 | 无 |
| 旧版全局指针显式恢复 | 任意 | 仅所有权可证明时恢复原值 | 不变 | 重启后使用原状态 | 仅恢复操作触发 |

还必须验证：

- `.codex` 非空但只有未知文件时不会被接管；
- `.codex` 为空但没有所有权标记时也不会被接管；
- 初始化中断不会留下有效所有权标记；
- 初始化中断后同一工作区可以通过 pending 预留恢复，其他工作区不能接管；
- 默认目录绑定后创建和切换其他工作区不会改变绑定；
- 多次启动幂等，不重复签发凭证或重写无关文件；
- 任意 GUI 程序无响应时，Connector 仍能在健康窗口内启动；
- 从百积木启动的 `codex app-server` 实际读取的是所选目录；
- 用户原始 `auth.json`、`config.toml`、会话和 MCP 配置逐字节保持不变。

桌面打开与安装状态还必须覆盖：

| 操作 | 桌面启动校验 | 安装/操作结果 |
| --- | --- | --- |
| 首次安装收尾自动打开 | 系统应用激活请求被接受 | 安装 `succeeded`，提示桌面启动请求已提交 |
| 首次安装收尾自动打开 | 启动命令或系统应用激活失败 | 安装仍为 `succeeded`，安装器记录 warning，并提示手动打开 |
| 已有个人配置且未自动激活工作区 | 不发起桌面打开 | 安装 `succeeded`，保留个人配置与现有桌面会话 |
| 管理页显式切换档案 | 系统应用激活请求被接受 | 切换成功 |
| 管理页显式切换档案 | 启动命令或系统应用激活失败 | HTTP 409，保留已提交的档案选择并返回明确错误 |

## 明确禁止的实现

- 仅以 `.codex` 目录是否存在判断是否允许初始化。
- Connector 每次启动都重写用户级 `CODEX_HOME`。
- Connector 在非 Windows AppX 显式激活流程中广播 `WM_SETTINGCHANGE`，或激活后不恢复原环境。
- 通过 Explorer/LaunchServices 的环境继承来猜测桌面 Codex 使用哪个状态目录。
- 把 Connector 私有环境变量原样传给 Codex 子进程。
- 把广播失败转换成健康失败、降级兼容分支或无限重试。
- 为了制造可见窗口而创建或打开合成项目、目录或文件。
- 用可见窗口、进程就绪或当前前台状态作为同步成功条件。
- 因安装收尾的桌面自动打开失败而把已完成的安装标记为失败或回滚档案。
- 为特定用户、工作区、环境或机器写固定分支。
- 在无法证明目录所有权时自动覆盖、合并或删除用户 Codex 状态。
